# Native Kernel Research

How to make OpenContainer's kernel "native, exactly the way WebContainers does it" — citation-backed
findings for replacing the hand-written TypeScript kernel core (VFS, tar, fd table, gunzip, path
resolution) with a Rust→WASM core. ≈30 primary sources fetched and read for this doc (list in §10).

## Executive summary

- **WebContainers' kernel is Rust compiled to WASM — not Node's C++, not V8.** Their own engineers say so: "WebAssembly and Rust are a crucial part of it" and "our kernel … heavily relies on WebAssembly's capability to operate with shared linear memory" (blog.stackblitz.com, §1).
- **Node's own JS (lib/*.js) runs in the browser's JS engine.** An HN commenter who disassembled their ~440KB wasm (azakai, §1) found: "libc-like filesystem code … built using the rust toolchain … they use the JS VM in the browser, and they've ported the Node.js runtime scripts to that environment" (HN, §1).
- **Processes ≈ Web Workers; each worker instantiates the WASM modules**; workers talk via SharedArrayBuffer + Atomics (synchronous cross-worker calls); COOP/COEP (or a Chromium Origin Trial) is required (§1).
- **Emscripten's MEMFS is JS, not C++** — verified from source: `src/lib/libmemfs.js` is `addToLibrary({ $MEMFS: … })` JS glue with JS-object inodes. Do NOT port it. Emscripten's *other* FS, WasmFS, **is** C++ (`system/lib/wasmfs/`) and is the right reference (§3).
- At launch WebContainers used a **custom npm client ("Turbo")**; today they run "the native versions of npm, pnpm, and yarn … up to 10x faster than local" (marketing claim, their site) (§2).
- Their registry traffic goes through a **StackBlitz npm proxy** (`nr.staticblitz.com` — visible in public issue titles), and `mount()` accepts a **binary snapshot** (`@webcontainer/snapshot`) — batch FS population is a first-class fast path (§2, §8).
- Recommended core language for OpenContainer: **Rust → wasm32-unknown-unknown** with a flat C-ABI (ptr/len) export surface; `tar` + `miniz_oxide`/`flate2` in the same module; single-threaded first (no SAB needed) since our kernel runs JS+WASM on one worker thread (§5, §9).
- The 3 biggest evidence-backed perf levers: (1) per-syscall cost — no JS allocation/observable per VFS op; (2) **whole-tarball native extraction** into VFS in ONE wasm call (amortizes the JS↔WASM boundary to ~2 calls per tarball); (3) async pipelining of fetch→gunzip while wasm extracts (§2, §6).
- Defensible marketing: "real Node.js stdlib + real npm/pnpm + a native Rust/WASM kernel" — the **same architectural class** as WebContainers. No public evidence they ever compiled Node's C++; a fresh native core is a difference of implementation, not kind (§7).
- Biggest unknowns: their exact tar/gunzip internals, worker pool sizing, snapshot format, and proxy behavior are closed-source (UNVERIFIED) (§8).

## 1. What WebContainers actually is (confirmed)

Facts (each from a fetched source):

- Product/API: a browser runtime running Node.js; `boot()` returns a WebContainer with `fs`, `spawn`, `mount( FileSystemTree | Uint8Array | ArrayBuffer )` ("binary snapshot generated by @webcontainer/snapshot"), `export('zip')`. "Booting WebContainer is an expensive operation. Only a single instance … can be booted concurrently." — https://webcontainers.io/api
- Marketing perf claims: "Run the native versions of npm, pnpm, and yarn, all in the browser … **up to 10x faster than local**"; "Run Wasm out of the box"; boots in milliseconds. — https://webcontainers.io/ and https://blog.stackblitz.com/posts/introducing-webcontainers/ ("Builds complete up to 20% faster and package installs complete >= 5x faster than yarn/npm"; "boot in milliseconds"; "virtualized TCP network stack that's mapped to your browser's ServiceWorker API").
- Node JS runs on the browser engine; kernel is Rust→WASM: "WebAssembly and Rust are a crucial part of it … WebAssembly is key to enable critical, CPU-bound tasks on the web, which abound in our **OS-like layers**. There is simply no way we could aspire to rival the performance of native toolchains if it did not exist … exposing your Rust code to the web through **wasm-bindgen**." — https://blog.stackblitz.com/posts/debugging-v8-webassembly/
  Corroboration (HN user "azakai" — widely known as Emscripten's author; that identity is background knowledge, the quote below is verbatim from the fetched thread): "The largest wasm file I see … is 440K … contains a bunch of **libc-like filesystem code**, and was **built using the rust toolchain**. So it doesn't look like v8 has been compiled to wasm here … they use the JS VM in the browser, and they've ported the Node.js runtime scripts to that environment." — HN thread 27223012, fetched via https://hn.algolia.com/api/v1/items/27223012 (canonical: https://news.ycombinator.com/item?id=27223012)
- Process/threading model: "it spawns quite a few Web Workers. In fact, as many as you want, since they **roughly map to OS processes**. Each one of these workers gets its own instantiation of our WebAssembly modules." — https://blog.stackblitz.com/posts/debugging-v8-webassembly/ ; "Under the hood, WebContainers use **SABs heavily for communication** … it allows for **synchronous communication between workers** by leveraging the **Atomics** APIs." — https://blog.stackblitz.com/posts/cross-browser-with-coop-coep/ ; "our kernel is practically best friends forever with WebAssembly **threads** and … **shared linear memory**." — https://blog.stackblitz.com/posts/the-atomic-waltz/ ; Rust crates used directly, e.g. parking-lot, wasm-bindgen nightly multithreading, `__wbindgen_thread_destroy()` (~1MiB per worker): https://blog.stackblitz.com/posts/thread-destroyer/
- Memory model: SharedArrayBuffer ⇒ page must be cross-origin isolated: `COOP: same-origin` + `COEP: require-corp` (or `credentialless`); on Chromium they instead ride an **Origin Trial** (`BootOptions.coep: 'none'` "will only work on Chromium-based browsers as long as an Origin Trial is supported"). — https://webcontainers.io/api , https://webcontainers.io/changelog , https://blog.stackblitz.com/posts/cross-browser-with-coop-coep/
- VFS internals: **not publicly documented** — "in-memory file system" is the only public description; the repo is closed and exists only as an issue hub ("This repository serves as a central hub for the GitHub issues"). — https://raw.githubusercontent.com/stackblitz/webcontainer-core/main/README.md
- Cross-engine proof that Node JS is ported, not compiled: Firefox support required polyfilling V8's `Error.prepareStackTrace` and other vendor APIs; "port a JS runtime to run on top of a different one"; heavy use of "message passing, WebAssembly and atomics". — https://blog.stackblitz.com/posts/supporting-firefox/ ; https://blog.stackblitz.com/posts/webcontainers-are-now-supported-on-firefox/ ("built entirely on web standardized APIs like WebAssembly and Service Workers", Bytecode Alliance collaboration)
- Syscalls/internalBinding crossing the JS↔WASM boundary: no public doc. UNVERIFIED beyond the above (Rust + wasm-bindgen + shared memory + Atomics).

Inference: WebContainers = "Node's JS stdlib on the browser engine + a Rust/WASM kernel underneath + workers-as-processes + SAB/Atomics IPC + ServiceWorker-based TCP". That is precisely the architecture OpenContainer already has (real lib/*.js, workers-as-processes) — except our kernel layer is TS instead of Rust/WASM. Swapping that layer in kind is legitimate; nothing requires porting Node's C++ (they didn't).

## 2. The npm install hot path

Facts:

- Today the product runs **real** npm/pnpm/yarn CLIs: "Run the native versions of npm, pnpm, and yarn, all in the browser, all in your app, up to 10x faster than local." — https://webcontainers.io/ ; the canonical quickstart spawns `npm i` — https://webcontainers.io/guides/running-processes
- At launch the speed partly came from a **custom client**: "It's using a custom npm client we've built called **Turbo**" (Eric Simons, CEO, answering "How? Isn't this using npm?") and "WebContainer's built in npm client is so fast that it runs a fresh install on every page load" — https://hn.algolia.com/api/v1/items/27223012 and https://blog.stackblitz.com/posts/introducing-webcontainers/
- Registry traffic is proxied by StackBlitz — public issue titles show resolutions against `https://nr.staticblitz.com/...` and "returns 400 from **StackBlitz npm proxy**" (so the worker does not hit registry.npmjs.org directly). — https://github.com/stackblitz/webcontainer-core/issues?q=npm+install (page fetched; titles: "npm install resolves `bn.js` to `https://nr.staticblitz.com/bn.js`", "Bug: `ajv-keywords@5.1.1` returns 400 from StackBlitz npm proxy", "export() leaves out large files npm wrote that nothing has read yet")
- `mount()` accepts a **binary snapshot blob** (`@webcontainer/snapshot`) — i.e. prebuilt/serialized trees are mounted in one call, not file-by-file. — https://webcontainers.io/api
- Tarball fetch/gunzip/tar-extract/cacache internals: **UNVERIFIED** — closed source, no blog post, no docs page describes them.

Inference (where their speed actually comes from, vs our JS-emulated kernel):
1. **Per-op cost.** npm's reify does ~10⁴–10⁵ fs ops (open/stat/readlink/mkdir/rename) for a 559-package tree. In WebContainers each op lands in Rust/WASM with no JS object churn, no promise/microtask hop, no per-op postMessage. Our TS VFS pays JS allocations + counted-macrotask completions per op (see the workaround comments in `kernel/natives/fs.ts` — the "Exit handler never called!" saga is the smoking gun that per-op JS overhead dominates).
2. **Batching at the boundary.** One wasm call per tarball (extract 100s of entries inside WASM) vs one JS function call per entry. The boundary cost is amortized ~2 calls/tarball instead of ~500.
3. **Parallelism.** fetch (browser network stack, HTTP/2) proceeds while WASM unarchives — streams are async by construction (see §6), so tarball N+1 downloads while tarball N is extracted; their worker-per-process model lets npm's own JS run on one thread while kernel work happens on WASM in the same worker between awaits.
4. A registry **proxy** (nr.staticblitz.com) gives them edge caching + connection reuse (h2 multiplexing handled by the browser's fetch stack either way; the proxy mostly helps cache-hit rates and CORS control) — plausible but UNVERIFIED as a speed factor.

## 3. Emscripten MEMFS anatomy (read from source)

Task said to fetch `library_memfs.cpp` / `library_syscall.cpp`; those paths 404 today. Verified current layout via GitHub tree pages: the JS libraries live in `src/lib/` (e.g. `src/lib/libmemfs.js`, `libfs.js`, `libsyscall.js`) and the C++ FS is `system/lib/wasmfs/`.

Facts — **MEMFS is JavaScript, not C++** (verified from raw source):

- `src/lib/libmemfs.js` begins `addToLibrary({ $MEMFS: { … } })` — a **JS library string-injected into the output**, not compiled C++. Inodes are plain JS objects: directories are `node.contents = {}` (a JS object map `name → node`); files are `node.contents = new Uint8Array(0)` + `node.usedBytes`, with geometric growth (×2 under 1MB, ×1.125 above) on expand. `parent.contents[name] = node` on create. — https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/lib/libmemfs.js
- fd table + path resolution are also JS: `FS_MAX_OPEN_FDS: 4096`; `FS.streams` array; `nextfd()` is a **linear scan** `for (fd = 0; fd <= 4096; fd++) if (!FS.streams[fd])`; `FS.lookupPath`, `FS.getPath` (walks parents), `FS.createStream`. — https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/lib/libfs.js ; syscalls map via `SYSCALLS.getStreamFromFD(fd)` → `FS.getStreamChecked` — https://raw.githubusercontent.com/emscripten-core/emscripten/main/src/lib/libsyscall.js
- License: "Emscripten is available under 2 licenses, the MIT license and the University of Illinois/NCSA Open Source License." — https://raw.githubusercontent.com/emscripten-core/emscripten/main/LICENSE

Facts — **WasmFS (emscripten's C++ FS) IS the native reference** (verified from raw source):

- fd table: `class FileTable { std::vector<std::shared_ptr<OpenFileState>> entries; std::recursive_mutex mutex; }`; `#define WASMFS_FD_MAX 4096` ("Copied from legacy FS"); `OpenFileState` = {`shared_ptr<File>`, position, oflags, recursive_mutex, use-count} and **caches `std::vector<Directory::Entry> dirents` at open** for stable getdents. — https://raw.githubusercontent.com/emscripten-core/emscripten/main/system/lib/wasmfs/file_table.h
- memory backend: `MemoryDataFile { std::vector<uint8_t> buffer; }`; `MemoryDirectory { std::vector<ChildEntry{std::string name; std::shared_ptr<File> child;}> entries; }` with the comment "**Use a vector instead of a map to save code size**" (linear `findEntry` scan); `MemorySymlink { std::string target; }`; pluggable `Backend` base class (`createFile/createDirectory/createSymlink`). — https://raw.githubusercontent.com/emscripten-core/emscripten/main/system/lib/wasmfs/memory_backend.h , https://raw.githubusercontent.com/emscripten-core/emscripten/main/system/lib/wasmfs/backend.h

Inference: Do **not** port MEMFS — it is the JS-side design we are trying to escape (it even has the same shape as our TS VFS: JS-object nodes, JS map children). Port/steal the **WasmFS design** instead: Vec fd-table, per-OpenFileState position/flags, dirent caching, vector-of-children (fine at our fanout; see §4 for when to use a map). MIT/UoI dual licensing is permissive — reading/borrowing designs is unproblematic; copying code requires attribution under MIT (fine).

## 4. Native WASM VFS prior art + recommended data structures

Facts (repos actually fetched):

- **wasi-libc** (C): "a libc for WebAssembly programs built on top of WASI system calls. It provides a wide array of POSIX-compatible C APIs … standard I/O, file I/O, filesystem manipulation …". The fd table and path ops live in libc/preopen land; fd semantics defined by WASI preview1 (`path_open`, `fd_read`…). — https://raw.githubusercontent.com/WebAssembly/wasi-libc/main/README.md
- **Wasmer `virtual-fs`** (Rust): async-trait based VFS abstraction layer (`ArcFile`, overlay/memfs backends), depends on `dashmap` (concurrent map), `tokio`; 616KB of source. — https://docs.rs/virtual-fs/latest/virtual_fs/ (repo: github.com/wasmerio/wasmer, `lib/virtual-fs`)
- **littlefs** (C, embedded): "All file operations have strong copy-on-write guarantees … recursion and dynamic memory is limited to **configurable buffers that can be provided statically**." Arena/static-allocation discipline worth copying; flash-oriented (wear leveling) — not a RAM VFS. — https://raw.githubusercontent.com/littlefs-project/littlefs/master/README.md
- **`tar` crate** (Rust): "utilities necessary to manage TAR archives **abstracted over a reader or writer** … an archive is **never required to be fully resident in memory** … largely a **streaming interface**"; security: "paths containing `..` are rejected, and symlink targets … validated before use." — https://docs.rs/tar/latest/tar/
- **`miniz_oxide`** (Rust): "A pure rust replacement for the miniz DEFLATE/zlib encoder/decoder. Used as a rust back-end for the **flate2** crate." MIT OR Zlib OR Apache-2.0. — https://docs.rs/miniz_oxide/latest/miniz_oxide/
- **libdeflate** (C): "heavily optimized … **significantly faster than the zlib library**, both for compression and decompression, and especially on x86 and ARM." — https://raw.githubusercontent.com/ebiggers/libdeflate/master/README.md
- Emscripten WasmFS (C++) — see §3.

Inference — recommended data structures for our core (concrete):
- **Inode arena**: `Vec<Inode>` indexed by `u32` inode id; `Inode { kind: Kind, parent: u32, name_range: (u32,u32) into a name arena, mode: u32, times: u64×4, children: ChildMap, data: DataRef }`. u32 indices (not pointers/shared_ptrs) → 4-byte parents, cache-dense, no per-node heap header. (WasmFS uses `shared_ptr` because it's C++ plumbing code in libc; we don't need refcounts — the kernel is single-owner.)
- **Children**: `HashMap<u32 /*child inode*/, ()>`? No — use **`HashMap<Box<str>, u32>` per directory only for dirs > 16 entries; below that a `SmallVec<(name, u32)>` with linear scan** (matches WasmFS's "vector to save code size" finding; npm dirs are small — node_modules subdirs rarely exceed ~30 entries, but `.bin` and top-level `node_modules` can hit thousands → HashMap there). Keep both behind one `ChildMap` enum so the hot path (`lookup`) stays monomorphic.
- **fd table**: `Vec<Option<FdSlot>>` with a free-list head (`u32` chain inside vacant slots) — O(1) alloc/free, no 4096 linear scan (that's an emscripten wart we shouldn't copy). `FdSlot { inode: u32, pos: u64, flags: u8 }` — flat 16 bytes, `copy_from_slice`-able for JS bulk reads.
- **Path strings**: intern segments in a byte arena (`Vec<u8>` + `HashMap<Range, u32>` only if needed); path resolution = split on `/` with `memchr`, walk parents by u32. **Never allocate per syscall**: all names live in a caller-owned scratch region of linear memory (see §5).
- **File data**: `Vec<u8>` per file (like `MemoryDataFile`) but with the same geometric-growth policy emscripten MEMFS uses (×2 <1MB, ×1.125 above) — that policy is verified in their source and is the right amortization for tar extraction.
- **Symlinks**: store target as (offset,len) into the name arena; resolve during walk with a loop-budget (ELOOP cap, 40 like Linux).
- **Mounts**: defer (our root is one memory FS; persistence mirrors via deltas like today).

## 5. JS↔WASM boundary design

Facts:

- WASM exports are ordinary callable functions on `Instance.exports`; memory is a growable `ArrayBuffer` (`memory.buffer`) shared by JS and WASM on the same thread. — https://developer.mozilla.org/en-US/docs/WebAssembly/JavaScript_interface
- `DecompressionStream` "implements the same shape as a TransformStream, allowing it to be used in ReadableStream.pipeThrough()" — i.e. **async by construction**; "available in Web Workers". — https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream
- wasm-bindgen exists precisely for "facilitating high-level interactions between Wasm modules and JavaScript" (WebContainers uses it) — but it is a *convenience* layer; the posts also show they fight its limits (nightly Rust, `__wbindgen_thread_destroy`). — https://raw.githubusercontent.com/rustwasm/wasm-bindgen/main/README.md ; https://blog.stackblitz.com/posts/thread-destroyer/
- WebContainers' IPC between *workers* is SAB+Atomics **because processes are separate workers** (§1). Inside one worker, JS and WASM share one thread and one linear memory — the boundary is a plain function call; there is no postMessage, no Atomics needed on that path. (MDN above; no source states the ns cost of a call — treat any specific number as UNVERIFIED.)

Inference — the design we should ship:
- **Flat C-ABI exports** `#[no_mangle] extern "C" fn oc_*(ptr: *const u8, len: u32, …) -> i32` — skip wasm-bindgen for the hot surface (its per-call marshalling and `JsValue` plumbing cost more than a raw call; wasm-bindgen is fine for tests/tooling). This mirrors what the 440KB WebContainers wasm looks like from outside (a plain module with a libc-ish surface).
- **Strings**: one persistent scratch buffer in linear memory (e.g. 64KB at a fixed offset). JS side: keep a module-level `TextEncoder` + write bytes into `wasm.memory` via a cached `Uint8Array` view; **re-create the view only after `memory.grow`** (`memory.buffer` detaches). Return (ptr,len) pairs for outbound strings; decode with one module-level `TextDecoder`. Zero per-call allocation on either side.
- **Bulk over single**: prefer few big calls (`oc_extract_tar`, `oc_read_dir_all`, `oc_stat_many`) over per-entry calls; per-call fixed overhead is the whole game (qualitatively; no public ns benchmark — UNVERIFIED, so we must measure ourselves in a micro-bench task).
- **Same-thread sync calls are the fast path** — our kernel lives inside the worker that runs Node's JS (see `kernel/worker-entry.ts`: "One worker = one Node.js process"), exactly like WebContainers' per-worker WASM instantiation (§1). No postMessage on the syscall path; postMessage/SAB only for host↔worker coordination we already have.
- Async fs ops (Node's threadpool-shaped API) stay async at the JS layer via our existing counted-macrotask completion (fs.ts), but the *work inside the completion* is one wasm call.

## 6. Gunzip strategy

Facts:

- `DecompressionStream('gzip')` is a **TransformStream** — asynchronous, stream-shaped; usable in workers. No public statement that any browser moves the work off the calling thread ⇒ treat "offloaded to another thread" as **UNVERIFIED** (assume it competes with our worker's JS unless measured). — https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream
- In-wasm decoders: `miniz_oxide` (pure-Rust miniz replacement, flate2's back-end — https://docs.rs/miniz_oxide/latest/miniz_oxide/); libdeflate is "significantly faster than zlib … especially on x86 and ARM" (https://raw.githubusercontent.com/ebiggers/libdeflate/master/README.md) but is C (needs a C toolchain target or a Rust binding). **GB/s throughput comparisons between DecompressionStream and wasm zlib in any authoritative public benchmark: UNVERIFIED** (searched HN/Algolia; only anecdotal uses of DecompressionStream as a pako replacement — https://hn.algolia.com/api/v1/search?query=%22DecompressionStream%22&tags=comment).
- Our worker already captures the host `DecompressionStream` before kernel global replacement and falls back to `fflate` (`__ocHostGunzip` in `kernel/worker-entry.ts`, read in-session) — so both paths exist today.

Inference: pipeline decision. Because the tar→VFS step must be *synchronous inside WASM* to be cheap, and gunzip is async either way (DecompressionStream is a stream; our own host bridge is promise-based), the clean split is:
`fetch(tarball) → gunzip (host DecompressionStream, already streaming; overlaps network) → bytes in wasm memory → ONE oc_extract_tar call`.
The gunzip stage does not need to be in WASM for the boundary cost to vanish — it produces one contiguous buffer that WASM consumes; only if profiling shows the host stream starves the worker (it's async, so it shouldn't) would we switch to `flate2`/`miniz_oxide` in the same module (also lets us drop the fflate fallback and the `fflate` dep). Keep `__ocHostGunzip` as the default, add `oc_gunzip` behind a flag, A/B on the 559-package benchmark.

## 7. Defensible "native" claims

Facts (recap from §1–§2, all cited above): WebContainers = browser-engine-executed Node stdlib JS + Rust/WASM kernel layer + workers-as-processes + SAB/Atomics + ServiceWorker TCP; their wasm at launch was ~440KB of "libc-like filesystem code … built using the rust toolchain"; no public evidence anywhere of Node/V8 C++ being compiled; their npm speed at launch included a custom client (Turbo) and today includes a registry proxy + snapshot mounts.

Inference — what WE can truthfully claim if we ship (real Node lib/*.js + real npm/pnpm + Rust/WASM core):
- ✅ "Node.js's real standard library, running in your browser's engine" — identical class to WebContainers (proven by their Firefox work: the JS is engine-portable).
- ✅ "Native kernel core: VFS, tar, fd table, path resolution, gunzip — compiled to WebAssembly" — this is *the same class* of statement WebContainers makes ("WebAssembly is key … abound in our OS-like layers").
- ✅ "Runs the real npm/pnpm CLIs" (already true).
- ❌ Do NOT claim: "Node.js compiled to WebAssembly" (false for them too — azakai), "same binary as local Node" (their Node is patched enough to need polyfills; ours is real lib/*.js but on a browser engine — say that exactly), or unqualified "10x faster than local" (that's their marketing of their stack; we must benchmark ours and publish the setup).
- Nuance for honesty: WebContainers *ports* the Node runtime scripts onto browser APIs and writes a fresh kernel in Rust — they did NOT port Node's C++ either (no public evidence). Therefore "we wrote a fresh native core instead of compiling Node's C++" is **a difference of implementation, not of kind**. Safe wording: "the same architecture as WebContainers: real Node stdlib on the browser engine, with the OS layer as native code (Rust→WASM) underneath."

## 8. Risks + unknowns (what we still can't see)

- Closed-source internals with zero public description: their exact tar extraction, gunzip choice, cacache layout, VFS data structures, worker pool sizing, wasm module list/sizes, and the `@webcontainer/snapshot` binary format. (Repo is an issue hub only — https://raw.githubusercontent.com/stackblitz/webcontainer-core/main/README.md)
- **Custom/patched npm?** Confirmed *historically* (Turbo at launch); today "native npm/pnpm/yarn" is claimed on their site, but the proxy (`nr.staticblitz.com`) could still rewrite/special-case metadata or tarballs. UNVERIFIED — treat their proxy as a potential cache/rewrite layer we don't have.
- **Prebuilt caches / snapshots**: `mount(binary snapshot)` is public API — they may ship pre-resolved trees for popular templates, which would make "install" partially a no-op for their demos. UNVERIFIED.
- HTTP/2 multiplexing: browser fetch does h2 automatically; the proxy's location (edge vs origin) affects latency. UNVERIFIED as a differentiator.
- Memory pressure is real: users observed ~550MB RSS per Chrome helper on a small React install (HN, same thread); WebContainers hit V8's 100-`WebAssembly.Memory` ceiling and ~1MiB/worker costs (their posts, §1). A 559-package tree in a `Vec<u8>`-per-file VFS is ~hundreds of MB of linear memory — our wasm memory growth policy and the delta-persistence path must be profiled, or we trade disk-black-hole for RAM-black-hole.
- Engine variance: their Atomic-Waltz/Apple-Silicon saga shows WASM-threads performance is engine/hardware sensitive; our single-threaded v1 avoids that class entirely (no SAB, no COOP/COEP requirement for embedders — a *feature* vs WebContainers, cite https://blog.stackblitz.com/posts/cross-browser-with-coop-coep/ as the requirement they carry).
- Compatibility treadmill (public issues): pnpm needs `node:sqlite`; native `.node` binaries can't execute; Node version pinning — see https://github.com/stackblitz/webcontainer-core/issues?q=npm+install . We will inherit the same treadmill with real Node 26 lib/*.js.

## 9. Recommended build plan for OpenContainer

**Language: Rust → wasm32-unknown-unknown** (not C++/emscripten). Reasons (all evidenced above): WebContainers' kernel is Rust (their posts); pure-Rust `tar` (streaming, security-checked) + `miniz_oxide`/`flate2` give us the whole install hot path with no JS glue; no emscripten JS-FS baggage; MIT/Apache-2.0/Zlib licensing across the board. C++ would drag in emscripten's JS runtime or wasi-libc preopens we don't need.

**Module layout** (new Cargo workspace at `src/packages/opencontainer/kernel/native-core/`):
- `native-core/src/lib.rs` — kernel entry: `oc_init()`, errno cell, version.
- `native-core/src/vfs.rs` — inode arena, fd table, ChildMap, symlink resolution (§4 structures).
- `native-core/src/path.rs` — POSIX path normalization/split (ports of `kernel/vfs.ts` semantics).
- `native-core/src/tar.rs` — `tar`-crate-based extractor writing straight into the VFS (one call per archive; rejects `..`, validates symlink targets — same guarantees as the crate).
- `native-core/src/gunzip.rs` — `miniz_oxide` (feature-gated `oc_gunzip`; default off, host `DecompressionStream` stays the decompressor — §6).
- `native-core/src/scratch.rs` — fixed-offset string scratch + name arena.
- `native-core/build.rs` — emit `exports.json` consumed by the TS binding generator.

**Exported API (flat C-ABI, all `(ptr,len)` for strings)**: `oc_init`, `oc_reset`, `oc_errno`, `oc_open`, `oc_close`, `oc_read(fd, buf, len)`, `oc_write`, `oc_pread`, `oc_stat`, `oc_lstat`, `oc_realpath`, `oc_mkdir`, `oc_unlink`, `oc_rmdir`, `oc_symlink`, `oc_readlink`, `oc_rename`, `oc_readdir_all` (flat arena of entries + count), `oc_extract_tar(tar_ptr, tar_len, base_ptr, base_len, flags) -> u32 entries`, `oc_gunzip(in, in_len, out, out_cap) -> i32`, `oc_scratch_ptr`, `oc_tree_snapshot` / `oc_tree_apply` (replace today's `VfsTree` JSON delta with a binary blob — same trick as `@webcontainer/snapshot`).

**Integration points (existing files, swap inside — no protocol changes)**:
- `kernel/vfs.ts` — becomes a thin binding: `Vfs` class delegates to wasm exports; keeps `VfsPersistOp`/`VfsTree` APIs by diffing after batch ops (snapshot import/export via `oc_tree_*`).
- `kernel/natives/fs.ts` — `internalBinding('fs')` sync paths call wasm directly (one JS frame + one wasm call); async paths keep the counted-macrotask completion but do their work in one wasm call.
- `kernel/worker-entry.ts` — at boot: fetch/inline the `.wasm`, `WebAssembly.instantiate`, wire `__ocWasm` handle into the kernel boot; npm-oc/pnpm-oc tarball decompression keeps `__ocHostGunzip`; add `oc_extract_tar` to the installer fast path (vendor `npm-oc/tar.js`, `pnpm-oc/installer.js` call it when the handle is present).
- Host `fs-read/readdir/stat/apply-ops` messages (protocol.ts) stay — they now serialize from the wasm snapshot instead of the TS tree.

**Build toolchain steps**: `rustup target add wasm32-unknown-unknown`; `[profile.release] opt-level="z", lto="fat", panic="abort", codegen-units=1`; no std threads, no allocator for the hot path (bump-arena inside scratch.rs; `wee_alloc` only if needed by `tar`); `wasm-opt -Oz` (binaryen) in a `Makefile`/bun script; output `native-core.wasm` into `vendor/` next to the runtime blobs with the same Cache-API warm path used for `.ocrt.gz` (see worker-entry.ts boot pipeline).

**Size budget**: ≤ 600KB raw / ≤ 250KB gzip for the whole kernel wasm. Anchor: WebContainers' launch-era kernel wasm was ~440KB (azakai, §1) doing libc-like FS work; `tar`+`miniz_oxide`+our VFS at `opt-level=z` lands in the same ballpark. Hard cap: 1MB raw — beyond that the boot cost hurts the "milliseconds" claim.

**Rollout order** (each step benchmarked on the 559-package Expo tree, current baseline 12+ min; WebContainers-class target ≤ 2m30s):
1. Micro-bench: wasm vs TS VFS on npm-reify op mix (open/stat/rename storm) — gate everything on this.
2. `oc_extract_tar` + `oc_open/read/stat` behind a flag in worker-entry; npm-oc uses it.
3. Swap full `internalBinding('fs')` onto wasm; keep TS VFS as fallback (`OC_KERNEL=ts|wasm`).
4. Binary snapshot import/export (`oc_tree_*`) replacing JSON VfsTree deltas.
5. Optional: `oc_gunzip` A/B; optional later: second wasm instance on a helper worker for tar extraction overlap (needs SAB or transferables — do NOT adopt COOP/COEP unless measured necessary).
